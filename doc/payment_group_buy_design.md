# 订阅阶梯拼团：Payment 实现设计

日期：2026-10-12

状态：Payment 拼团后端实现已存在于本地工作区，小程序首版已接续完成。当前进度和验证结果见第十一节；第十节保留开发前的历史核查。具体价格、奖励和成团时限由活动配置。

## 一、已确认的核心规则

1. 由 `backend/app/payment` 承接拼团交易与业务编排。
2. 拼团同时提供两种利益：购买价格更低，成团后还有额外权益。
3. 可选人数为 3、4、5 人，人数包含团长。按开团时选定的档位确定目标人数、团价和奖励。
4. 每位成员独立付款、独立获得权益，服务端确认合格付款后才计入有效人数。
5. 正式套餐在成团后开通，并发放额外权益；等待成团不消耗订阅时长。
6. 超时未成团，已付款的拼团订单进入全额退款流程；退款完成状态以渠道确认结果为准。
7. 分享卡片、小程序码及手动拼团码指向同一团。订单号作为购买凭证使用。

## 二、当前 Payment 的集成基础

| 文件 | 当前行为 | 拼团扩展点 |
| --- | --- | --- |
| `backend/app/payment/model/pay_order.py` | 分别保存支付状态和权益发放状态 | 关联拼团、区分购买方式，表达已付款待成团 |
| `backend/app/payment/service/pay_order_service.py` | 按订阅模板原价预下单 | 服务端读取活动档位，计算并锁定团价 |
| `backend/app/payment/service/pay_service.py` | 回调和主动查单汇入支付成功处理；支持退款和超时关单 | 复用支付事实，驱动拼团业务与退款任务 |
| `backend/app/payment/service/subscription_notifier.py` | 支付成功直接发放订阅，退款成功撤销订阅 | 普通购买和拼团购买分别编排履约 |
| `backend/app/payment/service/my_order_service.py` | 用户订单查询、状态刷新、关闭和移除 | 返回待成团、成团发放中及奖励状态 |
| `backend/app/access/service/subscription_service.py` | 创建和撤销订阅 | 作为套餐及订阅类奖励的实际发放能力 |

当前支付通知器是单实例。扩展时使用统一通知入口进行业务分派，不能通过再次注册通知器覆盖现有订阅处理器。

### 已核实的渠道约束

- 当前订阅预下单支持 `virtual` 和 `hupijiao`。
- 当前虎皮椒实现只支持整单全额退款。
- 当前退款成功处理会标记整笔订单已退款，并撤销对应订阅，不能直接作为退差价接口。
- 当前虚拟支付和虎皮椒均不能依靠远程关单阻止迟到付款。本地团过期或订单关闭后，仍需要处理真实到账。

因此，首版采用“按所选档位团价收款，成团履约，失败全额退款”的交易方式。

## 三、活动与价格规则

### 3.1 活动配置

- 活动名称、说明、开始和结束时间、状态。
- 适用业务类型、购买项编码；首个业务为订阅模板。
- 开放的 3／4／5 人档位及对应的每人价格。
- 每档普通成员奖励、团长额外奖励。
- 成团时限、待付款占位时限、可用支付渠道。
- 订单资格、用户参与次数、与其他活动奖励的叠加规则。

价格与奖励必须由后台显式配置，不把示例金额、示例赠送天数作为默认售卖规则。

### 3.2 档位锁定

- 选择 5 人团，需要 5 名有效已付款成员；3 人时仍为待成团。
- 正式开团后，不允许直接修改目标人数、单价或奖励。
- 活动修改影响之后新开的团，既有团使用开团快照。
- 订单金额使用团价快照，客户端提交人数档位或团标识，不提交可信价格。
- 同一团的后加入成员使用相同的价格和奖励规则快照。

需要保存活动规则版本、原价、团价、基础套餐内容以及奖励定义。当前订阅发放按模板编码读取实时模板，实施时必须补齐快照履约或不可变模板版本能力，防止下单后模板变更导致权益漂移。

## 四、建议的状态与流程

### 4.1 团状态

```text
draft（团长待付款）
  ├─ 团长付款确认 → forming（拼团中）
  │                    ├─ 有效人数达标 → succeeded（已成团）
  │                    ├─ 到期不足 → expired（未成团）
  │                    └─ 规则允许的取消 → cancelled（已取消）
  └─ 未付款超时 → cancelled
```

建议正式成团倒计时从团长付款确认后开始，截止时间同时受活动截止时间限制。两类超时分别处理：未支付订单超时、已开团后的成团超时。

### 4.2 成员状态

```text
reserved（占位待付款） → paid（付款确认）
        ↓                    ↓
     expired             refund_pending → refunded
```

有效人数按成员付款事实及退款状态计算。浏览邀请、点击加入、创建未支付订单均不增加有效人数。

占位需要截止时间。占位数量与有效人数共同限制可售名额，防止最后一个名额出现多笔有效付款。

### 4.3 支付、成团和履约分别表达

| 场景 | 订单支付状态 | 基础套餐履约状态 | 团／奖励状态 |
| --- | --- | --- | --- |
| 待付款 | pending | pending | 占位待付款 |
| 已付款，人数不足 | paid | pending | forming |
| 已成团，等待发放 | paid | pending | succeeded |
| 基础套餐已开通，奖励待补发 | paid | fulfilled | 奖励 pending／failed |
| 套餐与奖励已到账 | paid | fulfilled | 奖励 granted |
| 未成团，退款处理中 | refund_pending | pending | expired |
| 退款完成 | refunded | revoked | 对应奖励未发放或已回收 |

`paid=true` 不等于已经开通。支付确认、订单详情和拼团详情都需要返回团与奖励状态，前端根据明确状态展示文案。

### 4.4 成团与发放

1. 支付回调和主动查单通过统一校验，记录真实支付事实。
2. 以订单唯一标识确认成员付款，重复确认不重复增加人数。
3. 对团做并发控制，原子地判定是否达标并写入成团终态。
4. 持久化各订单的基础套餐发放任务和额外奖励任务。
5. 事务提交后执行发放；失败按独立任务重试。
6. 基础套餐和奖励均记录独立幂等标识及发放结果。

发放任务需要持久化，不能只依赖进程内后台任务。可采用事务内任务表／outbox，配合提交后唤醒和周期补偿。不能在持有最后一笔支付订单锁时同步锁定全团其他订单并调用外部服务；实施时统一锁顺序并验证并发行为。

现有支付成功入口会跳过已经 `fulfilled` 的订单，因此奖励补发必须有独立任务，不能依赖再次收到支付回调。

### 4.5 过期与退款

- 到期处理需要核实已发起支付的状态，再做最终成团判定。
- 终态一旦确定，迟到付款不能自动重新打开团。
- 团已满、已过期、已取消，或占位已失效后的到账，进入独立的退款处理。
- 每笔退款保存稳定的操作标识；渠道请求结果未知时先查证，不能无条件更换退款单号重试。
- 退款申请受理与退款成功分别记录。失败任务可重试，用户能查看退款进度。
- 退款回调与成团／履约处理需要互斥校验，避免已退款订单随后获得权益。

成团后主动退款、团长退款对其他成员及团长奖励的影响，属于需要另外确认的活动规则，不能在实现中隐式决定。

## 五、建议的数据结构

以下是逻辑模型，实际字段、外键及索引在实施时按现有 FBA 规范落地。

| 逻辑对象 | 主要内容 |
| --- | --- |
| `pay_group_buy_activity` | 适用购买项、活动时间、状态、参与资格、规则版本 |
| `pay_group_buy_tier` | 活动、3／4／5 人档、每人价格、奖励配置 |
| `pay_group_buy_team` | 团长、目标人数、状态、截止时间、分享码、规则快照 |
| `pay_group_buy_member` | 团、账号、支付订单、邀请人、占位和付款／退款状态 |
| `pay_group_buy_reward` | 领取人、来源团和订单、奖励快照、幂等键、发放／回收结果 |
| 履约／退款任务 | 操作类型、业务引用、状态、稳定幂等键、重试信息 |

`PayOrder` 建议增加：

- `purchase_mode`：`direct`／`group_buy`，存量订单按普通购买处理。
- 与拼团成员或拼团订单关系的明确关联。
- 价格和权益快照：可利用 `extra_data`，但不将团员关系和并发计数仅保存在 JSON 中。

保留 `biz_type='subscription_template'` 和 `item_code=模板编码` 的含义。购买内容与购买方式是两个维度，后续接入其他购买项时仍可使用同一拼团流程。

需要数据库约束支撑同团账号唯一、参团订单唯一、同活动有效参与限制和奖励幂等。账号不能用多笔订单在一个团中占多个有效人数。

## 六、服务职责与接口方向

### 6.1 服务划分

- 活动服务：配置、档位、适用范围和规则快照。
- 拼团服务：开团、占位、成员资格、有效人数、成团与终态。
- 拼团订单服务：服务端报价、创建 `PayOrder`、关联成员。
- `PayService`：支付渠道交互、支付事实确认、退款事实确认。
- 履约协调服务：成团后发放基础权益和奖励，管理独立重试任务。
- `access`：实际创建、续期和回收订阅权益。

API 负责参数和权限，业务编排放在 Service，数据库操作放在 CRUD。后台活动管理与用户开团／参团采用各自的权限边界。

### 6.2 拟议接口

以 `/api/v1/payment/group-buy` 为前缀：

| 接口 | 用途 |
| --- | --- |
| `GET /activities`、`GET /activities/{activity_id}` | 查看可售活动及档位 |
| `POST /teams` | 选择活动和人数档，创建团长待付款的团 |
| `GET /teams/my` | 我的拼团 |
| `GET /teams/{share_code}` | 脱敏的团详情及当前账号可执行操作 |
| `POST /teams/{share_code}/prepay` | 占位并按团价创建本人支付订单 |
| `POST /teams/{share_code}/verify-order` | 预览本人订单的参团资格，不绑定、不发放 |
| `POST /teams/{share_code}/join-by-order` | 确认关联符合资格的本人订单 |

管理端另外提供受管理权限保护的活动创建、修改、启停接口。以上均为设计接口，尚未实现。

现有支付确认及我的订单接口增加可选的拼团摘要，包含团状态、人数、截止时间和奖励状态。原有支付与履约字段保持各自的语义，普通购买正常使用原有流程。

## 七、分享与订单号入口

- 团分享标识与订单号分离。当前外部订单号还可用于登录／激活，不作为公开拼团凭证传播。
- 分享卡片、小程序码和手工拼团码解析到同一团。
- 登录及购买后返回原团详情，保留有效期内的邀请上下文。
- 浏览团详情不自动参团；确认参团和付款为明确操作。
- 拼团邀请人单独记录，不覆盖既有注册邀请关系。
- 站内订单校验本人归属、购买项、金额、支付状态、活动和档位，不允许重复占用。
- 外部订单通过真实来源核验及账号绑定接入，不伪造站内支付记录；仅能激活的订单号不自动等同于符合拼团支付资格。

需要进一步确认的订单号规则：

1. 以前按原价购买、已经激活的订单，是否允许补参加？
2. 如果允许，是只补额外权益，还是也需要价格优惠？后者需要单独的差额结算设计。
3. 外部渠道如何证明购买金额、时间、对应档位及退款状态？

这些规则确定前，不能把所有历史可兑换订单默认纳入团价交易。

## 八、页面接入

1. 套餐页：单买价与 3／4／5 人团价，对应奖励和开通条件。
2. 团详情：目标人数、有效人数、剩余时间、成员状态、本人订单、邀请操作。
3. 支付结果：区分已付款待成团、成团发放中、已到账。
4. 我的拼团：进行中、已成团、未成团，以及奖励和退款进度。
5. 我的订单：入口关联团详情，支付成功不直接展示为订阅已开通。
6. 订单号参团：先核验和展示结果，再由本人确认关联。

## 九、实施阶段与验收重点

### 阶段一：交易闭环

实现活动档位、团和成员、站内团价订单、成团履约、超时全额退款、任务重试与管理配置 API。

### 阶段二：用户与运营入口

接入套餐页、团详情、我的拼团、支付结果和管理端配置；加入分享卡片、小程序码及拼团码。

### 阶段三：订单来源扩展

在历史订单和外部渠道规则确定后，接入对应的订单资格适配及订单号参团。

关键验收用例：

- 3／4／5 人档正确报价，选择 5 人时不能在 3 人付款后提前成团。
- 未付款成员不计数，重复回调和主动查单不重复计数。
- 成团前不发正式套餐，成团后基础套餐和额外奖励各发一次。
- 活动和模板修改不改变已开团的价格与权益承诺。
- 最后一个名额并发参团，不能产生超额有效成员。
- 发放中断、奖励失败、任务重复执行均可恢复且不重复发放。
- 成团判定、主动退款和到期任务并发时，终态及权益结果一致。
- 未成团全额退款，退款申请失败／结果未知／重复回调可正确处理。
- 本地关单或团过期后的迟到付款不能误开通权益。
- 登录账号切换、他人订单、跨套餐／跨活动订单不能错误参团。
- 普通订阅支付、查单、发放、退款和我的订单功能继续通过回归测试。

### 10.3 必须落实的技术细节

**权益冻结覆盖发放及查询。** 只保存 `duration_days`、`tier_code` 或模板代码，无法保证权益不变。当前订阅以 `template_id` 关联模板及权益包，查询时仍读取关联关系和权益值。实施前选定完整的冻结路径：不可变模板及权益版本，或订阅快照及对应查询支持。套餐、普通成员奖励、团长奖励均走同一冻结策略；不能发放时再按活动当前值重算。

**通过持久化任务衔接支付与成团。** 付款入口可在其交易／订单事务内保存唯一的成员确认任务；任务提交后由消费者锁定团处理计数及成团，再创建发放任务。这样支付回调无需在持有当前订单锁时锁定其他成员订单。任务执行仍须核对订单退款事实、团终态、成员身份和占位资格。需要明确锁顺序，并以并发测试验证付款、到期、退款和履约互斥，而不是仅依赖应用层判断。

**到期先核实付款，再确定终态。** 到期后停止新占位；对既有支付请求执行渠道核对及必要的补偿，然后重新读取团及成员状态作最终判定。期间不持有团锁调用外部渠道。渠道结果未知时保留可观察、可重试的任务，不能直接宣称退款完成。已经写入过期／取消终态的团不再被迟到回调重新打开。

**退款请求具备稳定身份。** 外部调用之前提交退款操作及退款号；网络超时属于结果未知，不等于渠道拒绝。能查退款结果的渠道先查询；无法可靠自动查证的情况进入人工处理，不无限自动重发。渠道回调与任务领取统一更新同一退款操作，退款完成后阻断后续发放。

**参与限制要允许恢复本人流程。** 数据库保证同团同账号唯一、同订单唯一；活动有效参与限制须明确哪些状态仍占用资格。未付钱占位失效不应永久阻止本人继续购买；任何新订单的迟到到账仍要识别并退款，不能重新占据已出售的名额。

**渠道开售前逐项验收。** 现有普通购买支持一个渠道，不代表已经验证它能支持团价、等待成团后发货、全额退款及退款结果查证。活动只能启用已通过这些能力验证的渠道，未验证的渠道在拼团预下单时拒绝，不仅在前端隐藏。

### 10.4 不阻塞基础开发、但需要业务确认的边界

- 首批售卖套餐、各档团价、普通成员奖励、团长奖励、成团和占位时限：作为活动配置，开发时不填假定默认值。
- 成团后主动退款及团长退款的处理：规则尚未确定，不能自动决定其他成员权益或团长奖励的回收方式；用户入口和后台退款必须采用一致的拼团资格校验。
- 历史已激活订单、原价订单及外部渠道订单补参团：保留阶段三，资格校验和确认接口在规则与来源核验能力完成前不开放。
- 用户参与次数与奖励叠加：活动启用前必须显式选择规则，未配置时不让活动进入可售状态。
