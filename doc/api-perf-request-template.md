# 接口性能优化 - 请求模板

> 给 AI 助手发起接口优化任务时使用。复制下方"快速模板"或"完整模板"填空即可。
> 越上面的字段越关键，下面的字段越偏可选。

---

## 🚀 快速模板（单接口，最常用）

```markdown
### 接口优化任务

**路由**：GET /api/v1/xxx/yyy/zzz
**当前耗时**：约 XXXms（描述：稳定/抖动/峰值多少）
**期望耗时**：比如 100ms 以内
**调用场景**：比如 列表页打开必调 / 详情切换章节触发

[选填] 业务背景：
[选填] 已知线索：
[选填] 是否允许改 schema/索引：
```

## 📋 完整模板（信息齐全版）

```markdown
### 接口优化任务

#### 必填项

**接口路由**
GET /api/v1/xxx/yyy/zzz

**当前耗时**
- 平均：XXXms
- p50：XXXms
- p99：XXXms（可选）
- 是否抖动：稳定 / 偶发抖动 / 频繁抖动

**期望耗时**
比如 < 100ms / < 200ms / 越快越好 / 跟某接口持平

**调用场景**
- 触发位置：列表页 / 详情页 / 后台批量任务 / ...
- 调用频率：高频（每页必调）/ 中频 / 低频
- 用户感知：阻塞 UI / 后台静默 / ...

#### 选填项（给了能让我少猜 30%）

**业务背景**
比如：
- 这是首页首屏接口，慢了用户立刻流失
- 这是后台报表接口，慢点没关系但不能挂

**数据规模**
- 主表行数：~XX 万
- 单次返回：~XX 条
- 是否有大字段（JSONB / TEXT / BLOB）

**已知线索**
- 是否怀疑 N+1
- 是否最近改过相关代码
- 是否走了缓存
- 用户反馈关键词：xxx

**约束条件**
- 是否允许改 DDL（加索引、改字段、加表）
- 是否允许引入缓存
- 是否允许引入新依赖
- 是否需要保持向后兼容
```

## 📦 批量打包模板（一次给多个接口）

```markdown
### 批量接口优化任务

**全局背景**：比如 列表页整体慢、要做全站性能 sprint

**接口列表**：

| # | 路由 | 当前耗时 | 期望耗时 | 调用频率 | 备注 |
|---|---|---|---|---|---|
| 1 | GET /api/v1/qbank/banks/{id}/questions/all | 800ms | <300ms | 进入答题页 | |
| 2 | GET /api/v1/quest/list | 600ms | <200ms | 列表常调 | |
| 3 | POST /api/v1/practice/submit | 1200ms | <500ms | 提交答题 | 必须保证一致性 |

**期望产出**：
- [ ] 先全部分析链路 → 出诊断报告

```

## 📜 慢日志直投（最省事，AI 自己挑）

如果您后端能导出慢请求日志，直接贴 top N 即可。

```
2026-06-07 ... GET /api/v1/quest/list 200 800ms
2026-06-07 ... GET /api/v1/qbank/banks/1128/questions/all 200 1200ms
2026-06-07 ... POST /api/v1/practice/submit 200 1500ms
...
```

AI 会自动挑出"耗时 × 频率"最高的几个，给优化方案。

## 🎯 信息分级（什么必须给，什么可以省）

### 🔴 必须您给（我没法自己产生）

| 信息 | 为什么必须 |
|---|---|
| 接口路由 | 不给路由没法定位代码 |
| 当前耗时 | 没具体数字没法定收益预期 |
| 期望耗时 | 决定我做几刀（小幅 vs 极致） |
| 调用频率/场景 | 决定要不要做缓存 |

### 🟠 给了更好（不给也能查，但慢）

| 信息 | 不给的成本 |
|---|---|
| 数据规模 | 我得自己跑 EXPLAIN 估算 |
| 业务背景 | 可能选错优化方向 |
| 是否能改 DDL | 我会先按"不能改"做保守方案 |
| 是否高频缓存场景 | 倾向方案不同 |

### ✅ 我能自己查（不用您操心）

- 接口实现代码位置（grep 路由）
- 调用链：service → crud → model
- SQLAlchemy 模型定义、表结构、已有索引
- 已有缓存逻辑、中间件、拦截器
- 项目配置（db.py、conf.py、log.py）
- git 历史变更
- 类似接口的实现参考

## 💬 快速口令（不想写格式时）

为了让发起任务更顺手，可以用这些固定开头：

| 您说 | 我做 |
|---|---|
| **"优化接口 XXX"** | 走完整链路分析 + 出方案 + 等拍板 |
| **"看一下接口 XXX"** | 只诊断，不出方案，不改代码 |
| **"这接口能不能优化"** | 粗判：有空间 / 没空间 |
| **"按上次方法搞接口 XXX"** | 复用 chapter-progress 套路：埋点→量→改 |
| **"批量诊断这几个接口：..."** | 先全部分析，给打包诊断报告 |

实在懒得写，一句话也行：
> "GET /api/v1/quest/list 现在 800ms 太慢，能搞到 200 吗？列表常用"

## 🛠 我接到任务后的标准工作流

```
Step 1: 链路分析
  - 定位 router → service → crud → model
  - 列出所有 SQL 调用点
  - 标注嫌疑瓶颈（按概率排序）
  ↓
Step 2: 打分段计时埋点
  - perf_counter 包裹每段 SQL/CPU
  - loguru 单行输出（含 trace_id、关键参数）
  - 让您拿到真实数据再决定方向
  ↓
Step 3: 实测数据回流
  - 您贴日志给我
  - 我对照预期，重新评估瓶颈
  - 调整或确认方案
  ↓
Step 4: 落地代码改动
  - 一刀一刀来（先低风险高 ROI）
  - 每刀清晰列出：改了什么 / 风险 / 验证方式 / 预期收益
  ↓
Step 5: 验证 → 迭代 / 收尾
  - 您再跑一次基准
  - 命中预期就推进下一刀
  - 没命中就回 Step 3
  ↓
Step 6: 清理
  - 埋点降级 DEBUG（保留再次诊断能力）
  - 基准脚本归档到 backend/scratch/
```

## 🎚 优先级自助判断表

老板自己想先排个序时可以参考：

| 当前耗时 | 调用频率 | 优先级 |
|---|---|---|
| > 500ms | 高频 | 🔴 立刻 |
| 200-500ms | 高频 | 🟠 排期 |
| > 1000ms | 低频 | 🟠 排期 |
| 100-200ms | 高频 | 🟡 看情况 |
| < 100ms | 任何 | 🟢 不必 |
| 任何 | 极低频 | 🟢 不必 |

> **耗时 × 频率 = 用户感知度**，单看耗时容易决策错。

## 🚧 我会避免做的事（无需您每次叮嘱）

- 擅自改全局配置（pool_size、超时、连接 URL 等）→ 一定先告知
- 擅自改 DDL（加索引、改字段、加表）→ 一定先确认
- 引入新依赖 → 一定先告知
- 删除您看起来没用的代码（可能是您没说的功能）→ 不删
- 改动后不验证就交付 → 必跑 syntax / build
- 一次合并多刀（出问题难定位）→ 永远一刀一改一验证
