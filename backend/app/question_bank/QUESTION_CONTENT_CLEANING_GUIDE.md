# 题库内容存储与清洗规范

## 1. 目标

本文档用于统一题库内容的入库格式、清洗规则与多端消费约定，确保同一份题目数据可以同时服务于：

1. 管理端编辑与预览
2. C 端 Web 展示
3. 小程序端展示
4. `render_book` / `render_pdf` 题本生成

核心目标只有一句话：

1. **数据库中保存“可复用的标准内容”，不要保存某一端专用的最终渲染结果。**

---

## 2. 适用范围

当前主要适用于以下表与模块：

1. 题目：`study_question`
2. 选项：`study_question.options`
3. 解析：`study_question_analysis`
4. 材料：`study_question_material`
5. 题目-材料关联：`study_question_material_relation`
6. 题本渲染消费方：`backend/plugin/render_book`

当前代码中的关键消费字段：

1. [question.py](D:/100_Work/101_Program/Proj/fba/backend/app/question_bank/model/question.py) 中的：
   `Question.stem`、`Question.options`、`QuestionAnalysis.content`、`QuestionAnalysis.answer_data`、`QuestionMaterial.content`
2. [payload.py](D:/100_Work/101_Program/Proj/fba/backend/plugin/render_book/schema/payload.py) 中的：
   `stem_text`、`options`、`analysis_text`、`material_ids`、`source_label`
3. [payload_service.py](D:/100_Work/101_Program/Proj/fba/backend/plugin/render_book/service/payload_service.py) 中的：
   材料去重、来源短标签提取、题本 payload 组装逻辑

## 3. 推荐存储原则

### 3.1 一句话结论

推荐库存储格式为：

1. **HTML 富文本**
2. **数学公式保留原始 LaTeX 源码**
3. **图片存资源 URL 或资源 ID**
4. **表格使用标准 HTML table**
5. **题目、解析、材料分别存储**
6. **材料题通过关联关系表达，不要把材料正文复制到每一道题里**

### 3.2 为什么这样存

这样做的好处：

1. Web 可以直接做 HTML 渲染，再对公式进行二次渲染
2. 小程序可以基于 HTML + 公式源码做适配
3. PDF 渲染可以将 HTML/LaTeX 转成 XeLaTeX
4. 后续换前端框架或更换 PDF 模板时，不需要重新清洗整库

---

## 4. 不推荐的存储方式

以下做法不建议作为数据库主存储格式：

1. 纯文本
2. Word 导出的带大量内联样式 HTML
3. KaTeX 渲染后的 DOM 结果
4. MathJax 渲染后的 DOM 结果
5. 截图版公式
6. 把来源、年份、地区、题型等结构信息混在题干第一行

原因：

1. 纯文本会丢失结构，后续很难排版
2. 编辑器垃圾样式会让多端展示和 PDF 转换变得不稳定
3. KaTeX/MathJax DOM 是“某一端的最终展示结果”，不是通用内容源
4. 公式做成图片后，搜索、复制、无障碍、重新排版都会很差
5. 元信息混进正文后，后续筛选、拼题本、做来源短标签都会很被动

---

## 5. 字段级存储建议

### 5.1 题目主体

建议映射：

1. `study_question.stem`
   存题干正文，允许 HTML 富文本，公式保留 LaTeX
2. `study_question.type`
   存结构化题型编码：`single` / `multiple` / `judgement` / `fill` / `shortAnswer`
3. `study_question.knowledge_point`
   存结构化考点，不要只在正文里写“考点：xxx”
4. `study_question.default_score`
   存分值，不要把“本题 2 分”写进题干首行

清洗要求：

1. 题干只保留题目内容本身
2. “单选题”“多选题”“本题 2 分”“来源：xxx”这类元信息不要混入题干正文
3. 如果原始数据里有题号，如“1.”、“12.”，入库时应剥离，题号由业务层或题本层生成

### 5.2 选项

建议映射：

1. `study_question.options[].option_code`
   存 `A` / `B` / `C` / `D`
2. `study_question.options[].content`
   存选项正文，允许 HTML 富文本，公式保留 LaTeX

清洗要求：

1. 不要把 `A.`、`B.`、`C.` 写进选项内容字段
2. 选项内容只保留选项文本本身
3. 如果原始文本里是 `①②③④` 这类圈号，可保留字符语义，但不要依赖特定字体效果
4. 不要把四个选项拼成一个大字符串再靠正则拆

### 5.3 答案与解析

建议映射：

1. `study_question_analysis.answer_data`
   存结构化答案
2. `study_question_analysis.content`
   存解析正文，允许 HTML 富文本，公式保留 LaTeX

清洗要求：

1. 客观题正确答案应优先写入结构化 `answer_data`
2. 解析正文不要重复堆砌“正确答案：A”这类可结构化的信息
3. 如果是主观题，可在 `answer_data` 中保留参考答案结构，在 `content` 中保留完整解析

### 5.4 材料题

建议映射：

1. `study_question_material.title`
   存材料标题
2. `study_question_material.content`
   存材料正文，允许 HTML 富文本，公式保留 LaTeX
3. `study_question_material.source`
   存材料来源
4. `study_question_material.year`
   存年份
5. `study_question_material_relation`
   存材料与题目的关联关系

清洗要求：

1. 一段材料只存一次
2. 题目通过 `material_id` 关联材料
3. 不要把同一段材料复制到 5 道关联题的题干里
4. 不要把“根据下列材料，回答 1-5 题”这类提示重复写进每一道题的正文

这条非常重要，因为当前 [payload_service.py](D:/100_Work/101_Program/Proj/fba/backend/plugin/render_book/service/payload_service.py) 已经按 `material.id` 去重并单独渲染材料区，重复存正文只会导致：

1. 题库冗余
2. 预览重复
3. PDF 排版变长
4. 后续维护困难

## 6. 推荐内容格式

### 6.1 HTML 作为主内容格式

推荐保留的结构标签：

1. `p`
2. `br`
3. `strong`
4. `em`
5. `u`
6. `sub`
7. `sup`
8. `ul`
9. `ol`
10. `li`
11. `table`
12. `thead`
13. `tbody`
14. `tr`
15. `th`
16. `td`
17. `blockquote`
18. `img`
19. `div`
20. `span`

建议：

1. `div`、`span` 只在确有结构需要时保留
2. 尽量减少样式类和内联样式
3. 避免编辑器私有标签

### 6.2 数学公式必须保留原始 LaTeX

推荐写法：

1. 行内公式：`$x+y=10$`
2. 行间公式：`$$\frac{a+b}{2}$$`
3. 兼容写法：`\(...\)`、`\[...\]`

推荐示例：

```html
<p>已知 $x+y=10$，且 $x-y=2$，则 $x=$ ____。</p>
<p>由方程组可得：</p>
$$
\begin{cases}
x+y=10 \\
x-y=2
\end{cases}
$$
```

不推荐示例：

```html
<span class="katex">...</span>
```

```html
<mjx-container>...</mjx-container>
```

```html
<img src="公式截图.png" />
```

原因：

1. 原始 LaTeX 最利于多端渲染
2. PDF 模板可直接转 XeLaTeX
3. 后续需要改字号、换模板、导出 Word/PDF 时不会被卡死

---

## 7. 图片与表格清洗规范

### 7.1 图片

建议：

1. 数据库存图片 URL 或资源 ID
2. 图片标签尽量使用标准 `img`
3. 保留必要属性：`src`、`alt`
4. 图片应可被后续下载、转存 OSS、或统一做代理

不建议：

1. Base64 超长内嵌图片直接塞进正文
2. 粘贴本地临时路径图片
3. 把整段题干做成一张大图

### 7.2 表格

建议：

1. 使用标准 HTML 表格
2. 表头用 `th`
3. 数据单元格用 `td`
4. 尽量不要依赖复杂 `colspan` / `rowspan` 之外的花式布局

推荐示例：

```html
<table>
  <thead>
    <tr>
      <th>年份</th>
      <th>人数</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>2024</td>
      <td>120</td>
    </tr>
  </tbody>
</table>
```

## 8. 来源与元信息清洗建议

### 8.1 不要把元信息硬塞进正文

以下内容应尽量结构化，不要写进题干第一段：

1. 年份
2. 地区
3. 考试属性
4. 题型
5. 分值
6. 难度
7. 考点
8. 来源说明

### 8.2 兼容当前系统的建议

当前 `render_book` 会从题库名称、材料来源等字段中提取短来源标签，例如：

1. `2026 市地级 国考`
2. `2025 江苏 省考`

所以在当前阶段，至少要保证以下信息尽量清晰可解析：

1. `bank.name`
2. `material.source`
3. `material.year`

### 8.3 更长期的建议

后续如果要提升稳定性，建议增加独立结构字段或 `extra/json` 字段存：

1. `source_year`
2. `source_region`
3. `exam_type`
4. `source_text`

这样可以避免后续一直靠字符串正则猜来源。

## 9. 清洗规则

建议对历史数据统一做以下处理：

1. 去掉 Word/WPS 粘贴残留的内联样式
2. 去掉无意义的 `span` 嵌套
3. 去掉 `font-family`、`font-size`、`color`、`line-height` 等展示性样式
4. 去掉空段落、连续空格、零宽字符
5. 统一中文全角/半角括号与标点风格
6. 统一换行语义，不要同时混用大量 `<br>` 与空 `<p>`
7. 统一列表结构，不要用“1. 2. 3.”伪装列表
8. 统一图片地址策略
9. 将题号、题型、来源等正文外信息剥离
10. 将四个选项拆成结构化选项记录
11. 将答案拆成结构化 `answer_data`
12. 将材料正文拆到材料表，通过关系表关联题目

## 10. 多端消费建议

### 10.1 Web

推荐方式：

1. 先渲染 HTML
2. 对 HTML 中的 LaTeX 公式做二次渲染
3. 图片走统一资源域名或代理

不要在库里保存 KaTeX 渲染后的 HTML 结果，应该保存原始公式源码。

### 10.2 小程序

推荐方式：

1. 保留 HTML 主结构
2. 公式源码继续保留 LaTeX
3. 在小程序端按组件能力决定走公式组件、服务端转图、或预处理

不建议：

1. 为了适配小程序，直接把主库存储格式降级成纯文本

### 10.3 PDF

推荐方式：

1. `render_book` 负责从业务表组装统一 payload
2. `render_pdf` 负责模板渲染与 XeLaTeX 编译
3. 数据库存储的内容应尽量接近“语义内容”，而不是“浏览器最终样式”

这也是当前题本链路能够长期维护的关键。

---

## 11. 材料题专项规范

材料题建议采用如下模型：

1. 材料是独立实体
2. 每道题只关联 `material_ids`
3. 题目正文只保留本题真正题干
4. 材料标题、来源、年份保留在材料实体上

推荐结构：

1. 材料 A
2. 材料 A 关联第 1 题、第 2 题、第 3 题、第 4 题、第 5 题

不推荐结构：

1. 第 1 题题干里复制完整材料 A
2. 第 2 题题干里再复制一次材料 A
3. 第 3 题题干里再复制一次材料 A

---

## 12. 建议的入库最小标准

如果当前时间很紧，至少保证以下最低标准：

1. 题干、选项、解析、材料都存成可控 HTML
2. 公式保留原始 LaTeX
3. 选项拆结构
4. 答案拆结构
5. 材料独立存储并关联
6. 图片地址可长期访问
7. 不把 KaTeX DOM 直接入库

做到这 7 条，后面再做题本、前端、多端适配都会轻松很多。

## 13. 正反例

### 13.1 正例：题干

```html
<p>已知某班男生人数与女生人数之比为 $3:2$，全班共有 $40$ 人，则男生有多少人？</p>
```

### 13.2 正例：选项

1. A：`<p>16</p>`
2. B：`<p>24</p>`
3. C：`<p>30</p>`
4. D：`<p>36</p>`

### 13.3 正例：解析

```html
<p>设男生有 $3x$ 人，女生有 $2x$ 人，则全班共有 $5x=40$ 人。</p>
<p>所以 $x=8$，男生人数为 $3x=24$。</p>
```

### 13.4 正例：材料题

材料表：

```text
title = “给定资料”
content = “<p>……材料正文……</p>”
source = “2026 国考市地级”
year = 2026
```

题目表：

```text
stem = “根据上述材料，下列说法正确的是：”
material_ids = [123]
```

### 13.5 反例：不推荐入库

```html
<p><span style="font-family:宋体;font-size:14pt;">1. 【2026国考】根据下列材料回答1-5题……</span></p>
<p><span class="katex">...</span></p>
<p>A. 选项一 B. 选项二 C. 选项三 D. 选项四</p>
```

问题：

1. 题号混进正文
2. 来源混进正文
3. 材料题提示混进正文
4. 公式是前端渲染结果，不是源码
5. 选项没有结构化
6. Word 样式污染严重

## 14. 上线前检查清单

清洗完成后，至少检查以下项目：

1. 题干能在管理端正常显示
2. 选项已拆成结构化记录
3. 答案能从 `answer_data` 正常读取
4. 解析正文可正常显示
5. 材料题未重复存正文
6. 图片链接可访问
7. HTML 中没有大量无意义内联样式
8. 公式源码未丢失
9. Web 端可渲染
10. 小程序端至少有兼容方案
11. PDF 模板能正常转出
12. 来源、年份、地区信息尽量可结构化或可稳定提取

## 15. 推荐执行顺序

如果你接下来要批量清洗历史库，建议按下面顺序推进：

1. 先定义统一清洗输出格式
2. 先清题干、选项、解析、材料四类正文
3. 再拆结构化答案
4. 再补材料关联
5. 再处理来源、年份、地区等元信息
6. 最后抽样验证 Web、小程序、PDF 三端效果

这样最稳，且能尽快形成第一批可用数据。

## 16. 当前项目的落地结论

结合当前 `question_bank` 与 `render_book` 实现，现阶段最推荐的落地方案是：

1. **题目内容库存 HTML 富文本**
2. **数学公式库存原始 LaTeX**
3. **图片库存 URL / 资源 ID**
4. **材料题独立建材料实体并做关联**
5. **不要把某一端专用渲染结果直接入库**

后续无论是题本生成、Web 展示、小程序适配，都会以这套方案成本最低、可维护性最高。

## 17. 推荐的清洗输出中间结构

如果你接下来要写清洗脚本，强烈建议不要一边解析一边直接写库，而是先产出一份统一中间结构，再做入库。

推荐最小结构如下：

```json
{
  "question": {
    "type": "single",
    "stem": "<p>已知某班男生人数与女生人数之比为 $3:2$，全班共有 $40$ 人，则男生有多少人？</p>",
    "difficulty": "medium",
    "default_score": 1,
    "knowledge_point": ["比例计算"]
  },
  "options": [
    { "code": "A", "content": "<p>16</p>" },
    { "code": "B", "content": "<p>24</p>" },
    { "code": "C", "content": "<p>30</p>" },
    { "code": "D", "content": "<p>36</p>" }
  ],
  "analysis": {
    "answer_data": { "correct": "B" },
    "content": "<p>设男生有 $3x$ 人，女生有 $2x$ 人，则 $5x=40$，故 $x=8$，男生为 $24$ 人。</p>"
  },
  "materials": [],
  "relations": {
    "bank_name": "2026 国考市地级行测真题",
    "chapter_name": null,
    "material_ids": []
  },
  "source": {
    "year": 2026,
    "region": "市地级",
    "exam_type": "国考",
    "source_text": "2026 国考市地级"
  }
}
```

这样做的好处：

1. 清洗结果可以先人工抽查
2. 同一份结果可以同时喂给入库脚本和题本测试
3. 出问题时更容易定位是“解析阶段错”还是“入库阶段错”

## 18. 常见拆分规则建议

### 18.1 题号拆分

建议清洗掉以下前缀：

1. `1.`
2. `1、`
3. `1．`
4. `第1题`
5. `12.`

保留原则：

1. 题号属于展示层，不属于题目正文

### 18.2 选项拆分

常见原始格式：

1. `A. xxx B. yyy C. zzz D. www`
2. `A．xxx`
3. `A、xxx`
4. `（A）xxx`

建议拆分目标：

1. 统一抽成 `option_code`
2. 统一抽成 `content`
3. 去掉选项编码自身，不写进 `content`

### 18.3 来源拆分

常见原始格式：

1. `【2026国考市地级】`
2. `（2025 江苏省考）`
3. `来源：2024年广东省考`

建议处理：

1. 从正文剥离
2. 尽量提取 `year`
3. 尽量提取 `region`
4. 尽量提取 `exam_type`
5. 保留一份完整 `source_text`

### 18.4 材料题提示拆分

常见原始格式：

1. `根据下列材料，回答1-5题`
2. `阅读以下资料，完成下面题目`

建议处理：

1. 放到材料或题组层语义中
2. 不要重复写进每道题题干

## 19. PDF 友好型内容约束

因为这套数据最终还要进入 `render_pdf -> XeLaTeX`，所以清洗时最好顺手遵守以下约束：

1. 少用强展示性的 CSS
2. 少用复杂嵌套布局
3. 表格尽量规整
4. 图片宽高不要依赖浏览器计算
5. 公式用标准 LaTeX，不要混入前端私有节点
6. 避免用颜色表达唯一语义
7. 避免复制网页里不可见字符

简单说：

1. **要存“语义结构”，不要存“浏览器截图思维”的内容。**

## 20. 清洗优先级建议

如果时间非常紧，可以按下面优先级推进：

### P0：必须先做

1. 题干清洗为标准 HTML
2. 选项拆结构
3. 答案拆结构
4. 解析正文单独存
5. 材料正文独立存
6. 公式保留原始 LaTeX

### P1：上线前尽量做

1. 来源字段拆结构
2. 图片地址统一化
3. 表格规范化
4. 去除历史样式污染
5. 清理空标签与乱码字符

### P2：后续逐步优化

1. 补全更细的来源标签
2. 补全更稳定的地区/考试类型字段
3. 建立自动质检脚本
4. 建立清洗失败样本池

---

## 21. 建议增加的自动质检项

后面如果你要做批量清洗，建议脚本自动输出以下质检结果：

1. 无题干的题目数
2. 无选项的客观题数
3. 无答案的题目数
4. 无解析的题目数
5. 含 KaTeX DOM 的题目数
6. 含超长内联样式的题目数
7. 含 Base64 图片的题目数
8. 疑似材料重复写入题干的题目数
9. 来源无法解析的题目数
10. 公式疑似损坏的题目数

这样你后面不会只得到“清洗成功多少条”，还能知道脏数据主要集中在哪一类。
