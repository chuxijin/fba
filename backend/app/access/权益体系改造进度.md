## 1. 已完成的后端改造

### 1.1 配额:额度包模型(对应 PRD §7.2、§四)

**问题**:原来余额是 `(user, code, scope, cycle_key) → 单个标量`,一个周期只有一个桶。
于是 PRD 的两条硬要求在数学上无法表达:
- §7.2「优先扣即将失效的配额」—— 只有一个桶,没有"哪个先过期"
- §四「支持一次性消耗额度」—— `CycleType` 全是周期重置语义

**方案**:新增 `quota_grant` 表作为余额的唯一真相源。

```
backend/app/access/model/quota_grant.py      额度包(remaining_amount + expires_at)
backend/app/access/crud/crud_quota_grant.py  过期优先扣减 / 余额聚合 / exists_any
backend/app/access/engine/ledger.py          重写为额度包驱动
```

- **扣减顺序**:`ORDER BY expires_at ASC NULLS LAST, priority DESC, id ASC` —— 排序即业务规则
- **一次性额度**:`expires_at = NULL` 的包,与周期补账包并存,余额是两者之和
- **周期补账**:惰性生成,首次访问该周期时按订阅配置补一个 `expires_at = 周期末` 的包
- `quota_ledger` **保留但降级为纯审计流水**,新增 `grant_breakdown` JSONB 记录本次扣减命中了哪些包

> ⚠️ **为什么要 `grant_breakdown` 而不是单个 `grant_id`**:一次扣 3 次可能跨两个包
> (本月包剩 1 次 + 活动包剩 5 次)。退款时要按明细精确回补到原包,否则会把"即将过期的额度"
> 错误地退成"永不过期的额度"。

### 1.2 试看:从权益降级为策略(对应 PRD §3.2)

PRD 原文:「**不需要单独为用户定义或发放试看权益凭证**」。原实现正好相反 —— 试看是
`entitlement` + `pack_item` + 账本扣减,还要靠 `_filter_covered_trials` 补丁把这些
`*.trial` code 从"我的权益"里藏起来。**那个补丁的存在本身就是建模错误的证据**,现已删除。

新方案:`resource_rule` 加一列 `trial_policy JSONB`,与 `grant_mode` 平级。

```jsonc
{"mode": "ordinal",     "limit": 5}    // 前 5 道题      —— 无状态
{"mode": "fraction",    "ratio": 0.1}  // 前 10%         —— 无状态
{"mode": "excerpt",     "chars": 300}  // 前 300 字      —— 无状态
{"mode": "daily_count", "limit": 3}    // 每日 3 次      —— Redis 匿名计数
```

前三种**完全无状态**:引擎只需知道"当前请求的是第几个子资源",不查库不发凭证。
只有 `daily_count` 需要计数,用 Redis key `access:trial:{user}:{type}:{id}:{code}:{date}`,
计数器故障时**降级放行**(试看多给几次远好过把付费引导变成硬故障)。

实现:`backend/app/access/engine/evaluators/trial_policy.py`

### 1.3 责任链重排

```
旧: FreePass → Ownership(空实现) → SubscriptionAccess → DirectGrant → QuotaTrial
新: FreePass → SubscriptionAccess → DirectGrant → Metered → TrialPolicy
```

- 删除 `ownership.py`(纯空转)与 `quota_trial.py`(拆成 metered + trial_policy)
- **保留 `ReasonCode.OWNERSHIP`** —— V2 用它表示「题库作者访问自己的题库」
  (`question_bank_v2/service/access_service.py:39`),与"单点买断"无关,别误删
- `MeteredEvaluator` **只看额度包余额,不查订阅** —— 这样免费用户被活动赠送的额度天然可用
- 「曾有额度包但已耗尽」→ deny `QUOTA_EXHAUSTED`(引导升级);
  「从未有过额度包」→ pass,让位给试看兜底。两者产品语义不同

### 1.5 额度发放渠道(对应 PRD §六)

`common/reward/fulfiller.py` 的 `FeatureFulfiller` 原本是**空壳,只 log 不落库**,
导致 PRD §6.4「邀请 1 人送 10 次 AI 提问」、§6.5「5 次试用额度」、§6.6 积分兑换额度
**全部落不了地** —— 运营只能发整个订阅或发经验值。

已替换为 `QuotaFulfiller`,注册名 `quota`:

```python
reward_data = {
  "entitlement_code": "agent.grade.quota",
  "amount": 10,
  "expires_in_days": 30,   # 省略则永不过期
  "scope_key": "global",
  "source_key": "invite:12345",  # 幂等键,必填
}
```

### 1.6 audience_filter fail-closed(安全修复)

`engine/resolver.py` 原来是 `if not audience_attrs: return rules` —— 空画像时
**返回全部规则、跳过过滤**。而生产链路从不传 `audience_attrs`(全仓只有 `debug.py` 传过)。
结果:运营一旦配了 `audience_filter={'grade':'svip'}`,线上会**对所有人生效**,与定向意图相反。
现改为:带 `audience_filter` 的规则在无画像时不匹配。
